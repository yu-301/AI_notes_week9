§6.9

換手時的安全處理與金鑰推導

換手時從目前金鑰（水平）或 AMF 的 NH（垂直）推出新金鑰，靠 NCC 同步；垂直推導讓舊基地台算不出新金鑰。

TS 33.501 Rel-18｜更新於 2026-11-08

看簡報版

為什麼需要

手機移動時會從一個基地台換到另一個基地台，這叫換手（handover）。UE 和基地台之間的保護都靠 KgNB，所以換手時要回答兩個問題：新基地台用什麼金鑰？舊基地台會不會知道這把金鑰？

如果新舊基地台共用同一把金鑰，只要有一台基地台被攻破，手機之後經過的每一台基地台的通訊都會曝光。理想做法是每換一次手就換一把新金鑰，而且舊基地台算不出新金鑰，這就是前向安全（forward security）。難處在於換手要快，不可能每次都重新認證。

5G 的解法是金鑰鏈：KNG-RAN* 可以從目前的 KgNB 推（水平），也可以從只有 UE 和 AMF 算得出來的 NH 推（垂直）。4G 也是用 KeNB*、NH、NCC 這套設計待查證；5G 跟 4G 不同的地方是：換手過程會一併同步 NAS 與 AS 安全上下文（§6.9.2.2 NOTE 1），AMF 之間傳遞上下文時也不帶舊的 5G 安全上下文（§6.9.2.3.3）。

關鍵名詞

KNG-RAN* Key for target NG-RAN node
換手時算出的「下一把」基地台金鑰，換手完成後就當成新的 KgNB 使用（Annex A.11／A.12）。
NH Next Hop
由 KAMF 推出的中間金鑰，只有 UE 和 AMF 算得出來。第一個 NH 用初始 KgNB 當輸入，之後每個 NH 都用前一個 NH 當輸入，形成一條鏈（Annex A.10）。
NCC Next hop Chaining Counter
NH 鏈的編號。每把 KgNB 都對應一個 NCC；UE 靠它判斷要用哪一個 NH。
水平金鑰推導 Horizontal key derivation
從目前使用中的 KgNB 推出 KNG-RAN*。
垂直金鑰推導 Vertical key derivation
從 AMF 提供的 NH 推出 KNG-RAN*。
PCI / ARFCN-DL Physical Cell Identity / Absolute Radio Frequency Channel Number - Downlink
目標 cell 的實體識別碼與下行頻率；水平或垂直推導時都會綁進金鑰。
NASC NAS Container
N2 換手時目標 AMF 放進 HO Command 的 NAS 參數包，作用類似 NAS SMC。
水平 KAMF 推導 Horizontal KAMF derivation
換 AMF 時，來源 AMF 依本地政策從目前 KAMF 推出新的 KAMF（Annex A.13）。這是 NAS 層的事，和上面的 AS 水平推導不同。
比較項目水平金鑰推導垂直金鑰推導
KNG-RAN* 從哪裡推目前使用中的 KgNB未使用過的 NH
原料從哪來來源基地台自己就有NH 只有 UE 與 AMF 算得出，由 AMF 交給基地台
NCC不變變大；UE 反覆推算 NH，直到 NCC 一致
何時使用基地台手上沒有未使用的 {NH, NCC}，例如初始建立後的第一次 Xn 換手有未使用的 {NH, NCC} 時，Xn 換手的來源基地台必須用它；N2 換手一律由 AMF 給新 NH
都要綁定目標 PCI 與 ARFCN-DL（Annex A.11／A.12）
前向安全沒有：來源基地台算得出新金鑰有：新 NH 不經過舊基地台

運作流程

換手類型誰算 KNG-RAN*新的 {NH, NCC} 從哪來
Intra-gNB-CU（§6.9.2.3.1）同一個 gNB；依政策也可以保留原 KgNB（ng-eNB 不支援保留）有未使用的 NH 就垂直，否則水平
Xn（§6.9.2.3.2）來源基地台算好，交給目標基地台換手完成後，AMF 在 Path Switch Ack 中給目標基地台，供下一次換手使用
N2（§6.9.2.3.3）目標基地台用 AMF 給的 NH 計算AMF 收到 HANDOVER REQUIRED 時立刻算出新 NH
  1. AMF / UE初始建立 AS 安全時，由 KAMF 推出 KgNB（對應 NCC=0）和第一個 NH（NCC=1）。AMF 只把 KgNB 給 gNB，不給 NH；gNB 把 NCC 設為 0。
  2. 來源 gNBXn 換手時，有未使用的 {NH, NCC} 就做垂直推導，否則做水平推導；兩者都要綁定目標 PCI 與 ARFCN-DL，算出 KNG-RAN*。
  3. 來源 gNB → 目標 gNB把 {KNG-RAN*, NCC} 交給目標基地台，目標基地台直接拿來當 KgNB。NCC 放進 HO Command，經由來源基地台轉給 UE。
  4. UE收到的 NCC 和目前相同，就從目前的 KgNB 做水平推導；不同就反覆計算 NH 直到 NCC 一致，再做垂直推導。結果當作新的 KgNB。
  5. 目標 gNB → AMF送 Path Switch Request；AMF 把 NCC 加 1、算出新 NH，在 Path Switch Ack 中回給目標基地台。目標基地台存起來供下次換手，並刪除其他未使用的 {NH, NCC}。
  6. 來源 AMFN2 換手時，收到 HANDOVER REQUIRED 就把 NCC 加 1、算出新 NH。把 {NH, NCC}、KAMF、ngKSI、NAS COUNT 交給目標 AMF；也可依本地政策先做水平 KAMF 推導。
  7. 目標 AMF若 KAMF 有換或要換 NAS 演算法，就建立 NASC：內含 K_AMF_change_flag、下行 NAS COUNT、ngKSI、選定演算法和 NAS MAC。連同 {NH, NCC} 放進 HANDOVER REQUEST 給目標基地台。
  8. 目標 gNB用收到的 NH 加上目標 PCI、ARFCN-DL 算出 KNG-RAN* 當 KgNB，並把 NCC（以及 NASC，若有）放進 HO Command。
  9. UE若有 NASC，先檢查下行 NAS COUNT 沒被重放、驗證 NAS MAC；旗標為 1 就推出新 KAMF 並把 NAS COUNT 歸零。驗證失敗就中止換手，沿用舊的 NAS／AS 上下文。

白話解釋

把 KgNB 想成旅館房卡。水平推導像是退房時，櫃台用你現在這張卡加上新房號，直接做一張新卡給你：很快，但舊櫃台知道怎麼做，所以舊櫃台也能複製你的新卡。

垂直推導像是總公司（AMF）先寄一張新的「母卡」（NH）給下一間分館，新房卡由母卡做出來。舊分館從頭到尾沒看過這張母卡，就算它被駭了也進不了你的新房間。NCC 則是母卡上的流水號，你看號碼就知道自己該用第幾張母卡。

Xn 換手時，新母卡要等你搬進新分館後才寄到，所以這次的房卡仍是舊分館做的，要再換一次房才真正擺脫舊分館。這就是「兩跳後才有前向安全」。

常見考點

  • 水平和垂直金鑰推導差在哪？水平從目前的 KgNB 推，NCC 不變，來源基地台算得出新金鑰，所以沒有前向安全。垂直從 AMF 給的 NH 推，NCC 會變大，NH 只有 UE 和 AMF 算得出，所以有前向安全。兩者都要綁目標 PCI 與 ARFCN-DL（§6.9.2.1.1）。
  • 為什麼初始建立後的第一次 Xn 換手一定是水平推導？初始建立時 AMF 不把 NH 給 gNB，基地台手上沒有可用的 {NH, NCC}。NCC=1 的第一個 NH 永遠不會拿來推 KgNB，只是 NH 鏈的起點（§6.9.2.1.1 NOTE 2、NOTE 3）。
  • Xn 換手為什麼要「兩跳」才有前向安全？新的 {NH, NCC} 要等換手完成、Path Switch Ack 才送到目標基地台，只能留給下一次換手用；這一次的金鑰仍是來源基地台算的。目標基地台可以馬上做一次 intra-gNB-CU 換手，提早用上新 NH（§6.9.2.3.2 NOTE 1）。
  • N2 換手呢？來源 AMF 收到 HANDOVER REQUIRED 就先算新 NH，經目標 AMF 直接交給目標基地台，來源基地台拿不到這個 NH（§6.9.2.3.3）。
  • UE 怎麼知道要用水平還是垂直？看 HO Command 裡的 NCC：和目前 KgNB 的 NCC 相同就做水平；不同就反覆計算 NH 直到 NCC 一致，再做垂直（§6.9.2.3.4）。
  • 水平 KAMF 推導和 AS 的水平金鑰推導是同一件事嗎？不是。前者是換 AMF 時從舊 KAMF 推出新 KAMF（NAS 層，Annex A.13），會用 K_AMF_change_flag 通知 UE；後者是換基地台時從 KgNB 推出 KNG-RAN*（AS 層）。
  • NASC 裡的 NAS MAC 為什麼用 COUNT = 232−1？這個值不在正常 NAS COUNT 的範圍內，可以避免和一般 NAS 訊息的輸入重複。重放保護則靠 UE 檢查 NASC 裡的下行 NAS COUNT 有沒有重複（§6.9.2.3.3）。
  • 什麼情況可以完全不換 KgNB？只有 intra-gNB-CU 換手，由 gNB 依政策決定，並在 HO Command 中告訴 UE；ng-eNB 不支援保留（§6.9.2.3.1）。
  • 移動註冊更新（mobility registration update）時怎麼換 KAMF？來源 AMF 依本地政策，用目前 KAMF 和 Registration Request 的上行 NAS COUNT 做水平推導。目標 AMF 決定採用的話，就在 NAS SMC 中帶 K_AMF_change_flag=1，也可以改成重新認證（§6.9.3）。
