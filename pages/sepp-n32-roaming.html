§13.2

SEPP 與 N32 介面的漫遊安全

跨網訊令都經過 SEPP：N32-c 協商金鑰與政策，N32-f 用 JWE 加密，中間業者的修改要用 JWS 簽章。

TS 33.501 Rel-18｜更新於 2026-11-08

看簡報版

為什麼需要

漫遊時，拜訪網路（visited PLMN）的網元要向本籍網路（home PLMN）要認證向量、用戶資料，這些訊令會跨越兩家營運商。兩家之間通常不是直接連線，而是經過漫遊中介（Roaming Intermediary，RI），例如 IPX 業者或漫遊樞紐（Roaming Hub）。RI 有時需要看甚至改訊息內容，才能提供它的服務。

4G 以前，營運商之間用 SS7（2G/3G）或 Diameter（4G）經 IPX 交換訊令，協定本身大多沒有端到端的加密與來源驗證。能接入互連網路的人可以偽造訊息，查詢用戶位置或攔截簡訊。待查證（sources/ 尚無 4G 互連相關文件）

5G 在每個網路的邊界放一個安全邊緣保護代理（Security Edge Protection Proxy，SEPP），所有跨網路的控制面訊令都透過兩個 SEPP 之間的 N32 介面傳送。它要同時做到兩件事：機密欄位端到端加密，讓 RI 看不到；RI 被授權的修改要可以驗證、可以追查（§5.9.3.2、§13.2.1）。

關鍵名詞

SEPP Security Edge Protection Proxy
位在網路邊界的非透明代理，負責和對方 SEPP 互相認證、協商密碼套件、管理金鑰、隱藏內部拓樸，是內部網元對外的唯一出入口。
cSEPP / pSEPP consumer's SEPP / producer's SEPP
服務使用方網路的 SEPP 和服務提供方網路的 SEPP。
N32-c N32 control plane connection
兩個 SEPP 之間的管理用連線，用 TLS 保護，負責協商安全機制、交換參數與金鑰材料、回報錯誤。
N32-f N32 forwarding connection
實際轉送網元之間訊令的連線，用 TLS 或 PRINS 保護。
PRINS PRotocol for N32 INterconnect Security
§13.2 定義的 N32 應用層安全協定：SEPP 用 JWE 保護訊息，RI 用 JWS 簽署自己的修改。
RI Roaming Intermediary
兩家營運商之間的漫遊中介，例如 IPX（IP exchange service）業者（cIPX、pIPX）或漫遊樞紐；SEPP 之間最多經過兩個 RI。
JWE JSON Web Encryption（RFC 7516）
用 AEAD 演算法同時加密、做完整性保護的 JSON 格式；SEPP 之間用共享的對稱金鑰。
JWS JSON Web Signature（RFC 7515）
用私鑰簽章的 JSON 格式；RI 用它簽署自己做的修改。
N32-f context N32-f context
一組 N32-f 安全參數：context ID、對方 PLMN ID／SEPP ID／位址、session key、IV、計數器、修改政策、RI 的公鑰或憑證清單等。
保護政策 Data-type encryption policy / Modification policy
前者規定哪些資料類型要加密，後者規定 RI 可以改哪些欄位；兩者都由營運商設定，依漫遊夥伴分別訂定。
SEPP 之間的路徑N32-f 的保護方式（§13.1.2）
沒有 RITLS（N32-c、N32-f 用不同的 TLS 連線）
RI 只提供 IP 路由TLS 或 PRINS 擇一
RI 需要查看、修改或增加訊息內容必須用 PRINS
SEPP 改寫後的區塊（§13.2.4.2）內容JWE 的角色RI 看得到嗎
dataToIntegrityProtectclearTextEncapsulatedMessage（原始 HTTP 訊息，但扣掉要加密的值）＋ metadata（authorizedIPX ID、N32-f message ID、N32-f context ID）AAD：只做完整性保護看得到，可依修改政策改
dataToIntegrityProtectAndCipher需要加密的欄位值明文輸入：加密 + 完整性看不到

運作流程

  1. 兩個 SEPP建立互相認證的 TLS 連線作為 N32-c。SEPP 依對方憑證中的 PLMN-ID 找到對應的信任錨（trust anchor），只用那一組根憑證驗證憑證鏈（§13.1.2）。
  2. 兩個 SEPP協商安全機制：發起端依優先順序列出自己支援的 N32-f 保護機制，回應端依本地政策（例如路徑上有沒有 RI）選出 TLS 或 PRINS（§13.5）。
  3. 兩個 SEPP若選 PRINS，就在 N32-c 上交換參數：協商密碼套件、互給隨機產生的 N32-f context ID、交換 RI 的公鑰或憑證清單；也可以交換保護政策（§13.2.2.2）。
  4. 兩個 SEPP用 TLS exporter 從 N32-c 匯出 64 octets 的 N32-f master key，再用 N32-KDF（HKDF-Expand）推出兩對 session key 和兩對 IV salt，分別給兩個方向的 HTTP session 用。之後 N32-c 可以拆掉（§13.2.4.4.1）。
  5. cSEPP收到內部網元的 HTTP/2 訊息後，依保護政策把它改寫成兩個區塊：只需完整性保護的 dataToIntegrityProtect，以及要加密的 dataToIntegrityProtectAndCipher（§13.2.4.3）。
  6. cSEPP以 session key 為內容加密金鑰（"alg" 設為 "dir"）做 JWE：要加密的區塊當明文，另一塊當 AAD，產生密文和驗證標籤後，經 N32-f 送出（§13.2.4.4）。
  7. RI（cIPX、pIPX）只看得到明文區塊。依修改政策把要改的地方寫成 JSON Patch，附上自己的身分和 JWE 驗證標籤，再用私鑰做 JWS 簽章後附在訊息後面；就算沒有修改也要附 JWS（§13.2.4.5）。
  8. pSEPP驗證 JWE 標籤並解密，驗證每個 JWS 簽章，確認 RI 身分符合 authorizedIPX ID、修改符合政策、PLMN-ID 符合 N32-f context。都通過才套用修改，重組 HTTP 訊息轉給目標網元（§13.2.4.7）。

白話解釋

兩家公司（營運商）之間寄公文，中間要經過報關行（RI）。報關行需要看封面、偶爾補蓋章才能通關，但不能讓它看到公文裡的機密，也不能讓它亂改。

於是每家公司在門口設一個收發室（SEPP）。收發室把機密內容鎖進只有兩家收發室打得開的保險袋（JWE），封面則用透明封套，誰都看得到，但一動就會被發現。報關行想補註記，只能在旁邊另貼一張自己簽名的便條（JWS），寫明「我改了哪裡」；對方收發室會檢查簽名是不是合約上那家報關行、改的地方有沒有超出約定範圍，才照便條把公文改好交給內部。

常見考點

  • SEPP 的主要功能有哪些？當非透明代理；和對方 SEPP 互相認證、協商密碼套件、管理 N32 金鑰；隱藏內部拓樸；作為內部網元對外的唯一出入口；檢查對方 SEPP 有沒有權使用訊息中的 PLMN ID（§5.9.3.2）。
  • N32-c 和 N32-f 差在哪？N32-c 是管理用的 TLS 連線，負責協商安全機制、交換參數和金鑰材料、回報錯誤；N32-f 用來轉送網元之間的實際訊令（§13.2.1）。
  • 什麼時候用 TLS、什麼時候一定要用 PRINS？中間沒有 RI 就用 TLS；RI 只做 IP 路由時 TLS 或 PRINS 擇一；RI 要查看或修改內容時必須用 PRINS（§13.1.2）。
  • 為什麼不能讓 IPX 用逐段 TLS 就好？逐段 TLS 會讓每個 RI 都看得到、也改得了整則訊息。PRINS 讓機密欄位在 cSEPP 與 pSEPP 之間端到端加密，RI 只能改政策允許的欄位，而且每次修改都留下可驗證的簽章紀錄（§13.2.4.1）。
  • 哪些資料不論政策如何都必須在 N32-f 上加密？認證向量、密碼材料、位置資料（例如 Cell ID）、SMS over SBI 的簡訊內容、授權 token；SUPI 則是「應該」加密（§5.9.3.3）。
  • N32-f 的金鑰從哪來？為什麼要綁 context ID？從 N32-c 的 TLS session 匯出 master key，再以 HKDF-Expand 加上 "N32"、N32-f context ID 和標籤推出 session key 與 IV salt。AES-GCM 若重用 IV 可能洩漏完整性金鑰，所以重用 master key 時一定要換新的 context ID（§13.2.4.4.1）。
  • RI 沒有修改，為什麼還要附 JWS？避免別人把修改紀錄整段刪掉。JWS 裡還放了 JWE 驗證標籤，把修改綁定到這一則訊息，提供重放保護（§13.2.4.5）。
  • 怎麼防止 RI 把加密欄位搬到明文位置？基本驗證規則規定：需要加密的欄位不得被插到 JSON 物件的其他位置。接收端 SEPP 也要檢查 RI 有沒有把加密欄位移動或複製到會以明文回傳的位置（§13.2.3.4、§13.2.4.1）。
  • N32-c 交換到的保護政策和本地設定不一致怎麼辦？營運商通常在漫遊協議中事先約定政策，N32-c 的交換只是用來偵測設定錯誤。不一致時，依營運商政策回錯誤訊息給對方 SEPP，或產生本地警告（§13.2.3.6）。
