§13.4

服務化架構的網路功能授權（OAuth 2.0）

NRF 當授權伺服器發 access token，網元帶 token 呼叫服務，提供者驗過簽章與 claims 才放行。

TS 33.501 Rel-18｜更新於 2026-11-08

看簡報版

為什麼需要

5G 核心網採用服務化架構（Service Based Architecture，SBA）：AMF、UDM、SMF 等網路功能（Network Function，NF）都把能力包成 HTTP API 服務，彼此用 API 呼叫。這樣很彈性，但也代表網路裡任何一個網元在技術上都能呼叫任何一個 API。

雙向 TLS 認證（§13.3）只能回答「你是誰」，不能回答「你能做什麼」。如果沒有授權機制，一個被入侵或設定錯誤的網元，就可能向 UDM 拿走不該拿的用戶資料或認證資訊。§5.9.2 因此要求 NRF 擔任授權伺服器，並確保探索與註冊請求都經過授權。

4G 的 EPC 主要用點對點介面（例如 Diameter），連線對象是事先設定好的，授權大多靠介面與對端設定隱含達成。待查證（sources/ 尚無 4G 核心網相關文件）5G 改用標準的 OAuth 2.0：每次存取服務都要出示由 NRF 簽發、限定對象和範圍的存取權杖（§13.4.1.0）。

運作流程

  1. NF Service Producer透過 NF 註冊程序，向 NRF 註冊為 OAuth 2.0 資源伺服器；NF profile 中可以附上依服務使用者類型或實例設定的 additional scope。
  2. NF Service Consumer以 NF Instance Id 作為 client id，透過 NF 註冊或 OAM 向 NRF 註冊為用戶端，並和 NRF 完成雙向認證；NRF 以它憑證中的 NF Instance ID 識別它。
  3. NF Service Consumer送出 Nnrf_AccessToken_Get：帶自己的 NF Instance Id 與 NF type、想用的服務（scope）、目標 NF type 或指定實例，可再附 additional scope、S-NSSAI、PLMN ID。
  4. NRF比對請求中的 NF Instance ID、NF type、PLMN ID 是否和對方憑證或 NF profile 一致，再檢查授權（包含切片限制）。通過就產生權杖並用私鑰簽章或共享金鑰算 MAC，否則不發權杖。
  5. NF Service Consumer收到權杖後可以存起來，在有效期限內重複用來存取 scope、audience 涵蓋的服務。
  6. NF Service Consumer呼叫服務時附上權杖；雙方依 §13.3 互相認證。
  7. NF Service Producer先驗簽章或 MAC，再逐一檢查 subject、audience、切片、NF Set ID、scope、additional scope、到期時間；請求有附 CCA 時也可以一併驗證。
  8. NF Service Producer全部通過才執行服務並回應，否則依 OAuth 2.0 的錯誤格式拒絕。

白話解釋

把核心網想成一棟辦公大樓，各部門（網元）彼此提供服務。門禁卡（TLS 憑證）只證明「你是這棟樓的員工」，不代表你可以進人事室調資料。

所以要進某個部門辦事，得先去總務處（NRF）申請一張臨時通行證（access token）。通行證上寫著你是誰、能去哪個部門、能辦哪些事、幾點到期，還蓋了總務處的鋼印。部門櫃台看到通行證，會先驗鋼印，再核對你本人和通行證上寫的是否一致，以及要辦的事有沒有在許可範圍內，才幫你處理。

常見考點

  • OAuth 2.0 三個角色在 5G 對應誰？NRF 是授權伺服器，NF Service Consumer 是用戶端，NF Service Producer 是資源伺服器（§13.4.1.1.1）。
  • 5G 用哪一種 grant？為什麼？Client Credentials Grant（RFC 6749 §4.4）。網元之間呼叫服務沒有人類使用者需要同意，由網元用自己的身分直接向 NRF 換權杖（§13.4.1.0）。
  • 權杖怎麼保護？權杖是 JWT，用 JWS 保護：NRF 用私鑰簽章，服務提供者用 NRF 公鑰驗；或改用 MAC，這時 NRF 和服務提供者需要兩兩預先共享對稱金鑰（§13.4.1.0 NOTE 1a）。
  • 權杖可以撤銷嗎？不行，本規格不支援撤銷。改由營運商依政策設定到期時間，限制權杖的使用期間（§13.4.1.1.2 NOTE 2）。
  • 怎麼防止別的網元拿偷來的權杖用？直接通訊時，服務提供者檢查權杖 subject 的 NF Instance ID，必須和對方 TLS 用戶端憑證中的一致。經過 SCP 的間接通訊可以附上 CCA，讓服務提供者比對 CCA 和權杖的 subject（§13.4.1.1.2）。
  • 漫遊時權杖由誰簽發？vNRF 認證服務使用者、檢查參數後轉給 hNRF，由 hNRF 授權並簽發。subject 和 audience 都會附上 PLMN ID；服務提供者檢查請求中的 PLMN ID 與權杖一致，pSEPP 檢查 subject 的服務網路 PLMN ID 和對端相符（§13.4.1.2.2）。
  • vNRF 和 hNRF 是直接互相認證嗎？不是，只有遞移信任：vNRF↔vSEPP、vSEPP↔hSEPP、hSEPP↔hNRF 各自互相認證，所以兩個 NRF 只是隱含地互相認證（§13.4.1.2.2 NOTE）。
  • 經過 SCP 的間接通訊怎麼授權？服務使用者可以自己透過 SCP 向 NRF 拿權杖；採委派探索時，則由 SCP 代為向 NRF 取得權杖。不論哪種，服務提供者仍要自己認證服務使用者並驗證權杖（§13.4.1.3）。
  • OAuth 2.0 適用所有訊息嗎？沒用 token 怎麼辦？不適用於通知（notification）操作。不使用 token 時改用靜態授權：NRF 與服務提供者依本地政策判斷（§13.4.1.0、§13.3.0）。
