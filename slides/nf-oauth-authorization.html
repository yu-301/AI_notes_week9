§13.4

服務化架構的網路功能授權（OAuth 2.0）

NRF 當授權伺服器發 access token，網元帶 token 呼叫服務，提供者驗過簽章與 claims 才放行。

為什麼需要

  • SBA：網元都以 HTTP API 提供服務，技術上誰都能呼叫誰
  • TLS 只證明「你是誰」，不決定「你能做什麼」
  • 被入侵的網元可能向 UDM 拿走不該拿的資料
  • 5G 用 OAuth 2.0：每次存取都要出示 NRF 簽發的權杖

角色PLMN 內漫遊

權杖 claims 與檢查

Claim內容Producer 檢查
issuerNRF驗簽章或 MAC
subjectConsumer 的 NF Instance Id和 TLS 憑證一致
audienceProducer 的 NF type／實例符合自己
scope允許的服務涵蓋這次操作
expiration到期時間未過期
選用additional scope、切片、NF Set ID有就要相符

運作流程（1/2）：取得權杖

  1. Producer向 NRF 註冊為資源伺服器，可附 additional scope
  2. Consumer以 NF Instance Id 註冊為用戶端，與 NRF 雙向認證
  3. ConsumerNnrf_AccessToken_Get：自己的身分、scope、目標 NF type
  4. NRF比對憑證或 NF profile、檢查授權，通過才簽發權杖

運作流程（2/2）：使用權杖

  1. Consumer存下權杖，有效期內可重複使用
  2. Consumer呼叫服務時附上權杖，雙方互相認證
  3. Producer驗簽章，再查 subject、audience、scope、到期時間
  4. Producer全數通過才執行，否則回 OAuth 2.0 錯誤

白話解釋

門禁卡（TLS 憑證）只證明你是大樓員工，不代表能進人事室。

要辦事得先向總務處（NRF）領臨時通行證（token），上面寫明你是誰、去哪、辦什麼、何時到期並蓋鋼印；櫃台驗過鋼印、核對本人與範圍才放行。

常見考點（1/3）

  • 三個角色？NRF 授權伺服器、Consumer 用戶端、Producer 資源伺服器
  • 哪種 grant？Client Credentials Grant，沒有人類使用者
  • 權杖怎麼保護？JWT + JWS：NRF 私鑰簽章，或預共享金鑰算 MAC

常見考點（2/3）

  • 能撤銷權杖嗎？不支援，靠到期時間限制
  • 防偷用權杖？subject 比對 TLS 憑證；間接通訊可用 CCA
  • 漫遊誰簽發？vNRF 轉送、hNRF 簽發；pSEPP 檢查 PLMN ID

常見考點（3/3）

  • vNRF、hNRF 直接互認？不是，經 SEPP 的遞移信任
  • 經過 SCP 怎麼辦？SCP 可代拿權杖，Producer 仍自己驗證
  • 適用所有訊息嗎？不適用通知；不用 token 時改靜態授權
