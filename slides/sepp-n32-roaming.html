§13.2

SEPP 與 N32 介面的漫遊安全

跨網訊令都經過 SEPP：N32-c 協商金鑰與政策，N32-f 用 JWE 加密，中間業者的修改要用 JWS 簽章。

為什麼需要

  • 漫遊訊令跨越兩家營運商，中間還有 IPX、漫遊樞紐等 RI
  • 4G 以前的 SS7／Diameter 互連缺乏端到端保護（待查證）
  • 5G 在網路邊界放 SEPP，跨網訊令一律走 N32
  • 目標：機密欄位端到端加密，RI 的修改可驗證、可追查

關鍵名詞

SEPP Security Edge Protection Proxy
網路邊界的安全代理
N32-c / N32-f N32 control plane / forwarding connection
管理用連線／轉送訊令
PRINS PRotocol for N32 INterconnect Security
N32 的應用層安全協定
RI Roaming Intermediary
IPX、漫遊樞紐，最多兩個
JWE / JWS JSON Web Encryption / Signature
SEPP 加密／RI 簽修改

N32-f 用 TLS 還是 PRINS

SEPP 之間的路徑N32-f 保護方式
沒有 RITLS
RI 只做 IP 路由TLS 或 PRINS
RI 要查看或修改內容必須 PRINS

SEPP 把訊息拆成兩塊

區塊JWE 角色RI 看得到嗎
dataToIntegrityProtect（明文訊息 + metadata）AAD，只做完整性看得到，可依政策改
dataToIntegrityProtectAndCipher（要加密的值）明文輸入，加密 + 完整性看不到

運作流程（1/2）：N32-c 建立

  1. 兩個 SEPP互相認證的 TLS 建 N32-c，依 PLMN-ID 選信任錨驗證憑證
  2. 兩個 SEPP協商安全機制：回應端依政策選 TLS 或 PRINS
  3. 兩個 SEPPPRINS：協商密碼套件、互給 context ID、交換 RI 公鑰與政策
  4. 兩個 SEPPTLS exporter 匯出 master key，HKDF 推出 session key 與 IV salt

運作流程（2/2）：N32-f 傳送

  1. cSEPP依政策把訊息拆成只做完整性、要加密兩塊
  2. cSEPP用 session key 做 JWE，經 N32-f 送出
  3. RI把修改寫成 JSON Patch，附 JWE 標籤後以 JWS 簽章
  4. pSEPP驗 JWE、驗 JWS、查政策與 PLMN-ID，再套用修改轉給網元

白話解釋

兩家公司在門口各設收發室（SEPP）：機密內容鎖進只有兩間收發室打得開的保險袋（JWE），封面用透明封套，一動就會被發現。

中間的報關行（RI）要補註記，只能另貼自己簽名的便條（JWS）；對方收發室核對簽名和約定範圍後才照改。

常見考點（1/3）

  • SEPP 做什麼？互相認證、協商套件、管金鑰、隱藏拓樸、唯一出入口
  • N32-c vs N32-f？N32-c 管理與協商；N32-f 轉送實際訊令
  • 何時必須用 PRINS？RI 要查看或修改訊息內容時

常見考點（2/3）

  • 為何不用逐段 TLS？RI 會看到、改到全部；PRINS 端到端加密機密欄位
  • 一定要加密的資料？認證向量、密碼材料、位置、簡訊內容、授權 token
  • 為何金鑰綁 context ID？避免 AES-GCM 重用 IV 洩漏完整性金鑰

常見考點（3/3）

  • 沒修改也要附 JWS？防止修改紀錄被刪；附 JWE 標籤防重放
  • 防 RI 搬移加密欄位？加密欄位不得移位，接收端 SEPP 要檢查
  • 交換到的政策不一致？依營運商政策回錯誤或產生本地警告
