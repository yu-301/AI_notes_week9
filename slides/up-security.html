§6.6

使用者平面（UP）安全與完整性保護

5G 讓使用者資料也能做完整性保護：SMF 依 PDU session 下政策，基地台再逐條 DRB 啟用加密與完整性。

為什麼需要

  • UP 是使用者真正傳的資料，由 PDCP 層保護
  • 只加密防不了竄改：密文翻位元，明文跟著翻
  • 4G 的 UP 只加密，曾被 aLTEr 竄改 DNS（待查證）
  • 5G：UE、gNB 必須支援 UP 完整性，是否使用看政策

關鍵名詞

UP User Plane
承載使用者資料
DRB Data Radio Bearer
資料無線承載，逐條啟用保護
SMF Session Management Function
管 PDU session、下政策
UP 安全政策 UP security policy
加密／完整性要不要開
MAC-I Message Authentication Code for Integrity
PDCP 封包的完整性驗證碼

UP 安全政策的三種值

值基地台的處理
Required一定啟用；做不到就拒絕並回報 SMF
Preferred基地台決定；換手後可能改變
Not needed不啟用，session 照常建立

4G 與 5G 的 UP 保護

項目4G5G
UP 加密有必須支援，依政策啟用
UP 完整性沒有（待查證）必須支援，依政策啟用，不得用 NIA0
支援速率—UE 最高速率下也要能做
啟用單位—政策以 PDU session，啟用以 DRB

運作流程（1/2）：政策下達

  1. SMF建立 PDU session 時送出 UP 安全政策
  2. gNBRequired 做不到就拒絕；ng-eNB 需 UE 支援 EIA7
  3. gNB確認 AS SMC 已啟動 RRC 安全
  4. gNBRRC Reconfiguration 逐條 DRB 標示保護，需要時推導 UP 金鑰

運作流程（2/2）：啟用與換手

  1. UE驗證 RRC 訊息，推導 UP 金鑰並開始保護
  2. UE回 RRC Reconfiguration Complete
  3. UE / gNB每個封包算 MAC-I，錯誤或缺少就丟棄
  4. gNB → SMF換手時傳遞政策，Path-Switch 由 SMF 比對

白話解釋

4G 的資料像裝在不透明信封裡：看不到內容，卻能用針戳洞改掉某個字，收件人察覺不到。

5G 可以再加封口貼紙（MAC-I）。總公司（SMF）決定哪類信一定要貼，郵局（基地台）逐個郵袋（DRB）照辦。

常見考點（1/3）

  • 為什麼 4G UP 沒有完整性保護？嫌 MAC 負擔與運算量大；但加密防不了位元翻轉（待查證）
  • 5G 改成怎樣？UE、gNB 必須支援（含最高速率），由 SMF 政策決定是否啟用
  • 為什麼不是必須使用？封包變大、運算變重，交給政策決定

常見考點（2/3）

  • UP 完整性能選 NIA0 嗎？不行，只多 32-bit MAC 沒安全效果
  • Required 做不到？拒絕 UP 資源並回報 SMF，基地台不得推翻
  • UP 安全何時啟動？AS SMC 之後，新增 DRB 時逐條啟用

常見考點（3/3）

  • 換手怎麼防政策被改？Path-Switch 時 SMF 比對，不符就送回正確版本
  • ng-eNB 能做 UP 完整性嗎？UE 設 EIA7 位元才行，可用 NIA 或 EIA
